# Static Netlify port: design

**Date** 2026-08-17
**Scope** A second frontend for the same data: React plus DuckDB-WASM, served
statically from Netlify, at full parity with the Reflex app, maintained
alongside it rather than replacing it.

## Goal

The Reflex app on Render needs a live Python backend, so it pays a free-tier
cold start on every idle period and cannot be served from a static host. A
static build with the query engine in the browser has no backend, no cold
start, and no hosting cost.

Both versions stay. Render remains the canonical app; Netlify becomes a fast
public showcase of the same data.

## The facts that shaped this design

Measured against the current codebase rather than assumed:

| | |
|---|---|
| `queries.py` | 1,152 lines, 49 public functions |
| Query functions with **static** SQL | 15 |
| Query functions that **build SQL dynamically** | 17 |
| Charts | 36 across 7 pages |
| Views blocked in Reflex by a missing Recharts mark | 1 (month-by-year heatmap) |
| Committed parquet | 12 MB, 14 files |
| Design tokens | 216 lines across `palette.py` and `theme.py` |

The split between static and dynamic SQL is the fact that shaped everything
else. Sharing `.sql` files covers 15 of 32 query functions. The other 17
construct SQL at runtime, and they are the hard ones: `_mart_where` runs a
probe query to discover which `is_total` flag combination maximises year
coverage, then builds a WHERE clause from the result. It exists because ISTAT
publishes different cross-tab slices in different years, so no fixed rule
survives contact with the data. That is an algorithm emitting SQL, not SQL.

So the design needs two mechanisms: sharing where sharing is possible, and a
mechanical check on the duplication that is not.

## Architecture

```
shared/
  queries/*.sql        the 15 static queries, one source of truth
  palette.json         generated from palette.py, never hand-edited
  palette.css          generated: the --div-N custom properties
  conformance/
    cases.json         {function, args} matrix over all 32 query functions
    expected.json      generated by Python, committed, reviewed on change
web/                   React + Vite + TypeScript + DuckDB-WASM
  src/db.ts            wasm bootstrap, parquet registration over HTTP
  src/queries/         TS ports of the 17 dynamic builders
  src/charts/          Observable Plot marks (NOT Recharts: see Charts)
  src/pages/           the 7 pages
  src/theme.ts         reads palette.json
italy_dashboard/       unchanged, except queries.py loads its static SQL
                       from shared/queries/ instead of inline strings
```

The Reflex app keeps working exactly as it does today. The only change inside
`italy_dashboard/` is where its static SQL text comes from.

## Shared SQL

Plain `.sql` files with positional `?` parameters. DuckDB uses the same
placeholder in the Python client and in WASM, so one file genuinely serves
both without a translation layer.

Positional parameters are a trap without documentation, so every file carries
a header comment naming its parameters in order and stating what it returns.

Python reads them from disk at import. Vite imports them with `?raw`.

A test asserts every file in `shared/queries/` is referenced from both sides,
so a query that falls out of use on one side cannot rot unnoticed.

## Palette as a generated artifact

`palette.py` remains the source of truth: it is the file the colour validator
checks and the golden tests pin. A generator script emits `shared/palette.json`
and `shared/palette.css`, the latter carrying the `--div-0` through `--div-6`
custom properties the warming stripes already depend on.

`theme.ts` reads the JSON. Nothing in `web/` hardcodes a colour.

A test regenerates both artifacts and asserts byte equality with the committed
copies, so editing `palette.py` without regenerating fails the build. This is
the same principle as the palette validator itself: the edit cannot be
prevented, so it is made impossible to land silently.

## Conformance suite

This is the mechanism that makes two implementations sustainable, and the part
of the design most worth getting right.

`shared/conformance/cases.json` lists function-and-argument pairs covering all
32 query functions. Coverage must include the awkward paths, not just the happy
ones:

- `_mart_where`'s probe behaviour, where the chosen flag combination depends on
  what the data actually contains
- queries that legitimately return empty, such as `climate_stripes` when the
  CLINO coverage guard nulls every anomaly
- the partial-coverage state, where climate data exists for a subset of regions

Python runs every case against the committed parquet and writes
`expected.json`. A Node test runs the identical cases through DuckDB-WASM and
asserts deep equality.

Floats compare at the precision the UI displays, not at full double precision:
the two engines are the same DuckDB build, but the round trip through JSON and
JavaScript numbers makes exact bitwise equality a brittle thing to demand.

Regenerating `expected.json` is a deliberate, reviewable step. A Python query
fix that changes output appears as a diff in a committed file. A TypeScript
port that drifts fails the build. Duplication that cannot be avoided becomes
duplication that cannot be silently broken.

## Data delivery

Netlify serves the committed parquet as static assets. DuckDB-WASM reads them
over HTTP range requests, so a query touching one column of
`mart_climate_annual` does not pull the whole file.

**One documented exception.** `mart_climate_daily` is 8.1 MB and exists for a
single view, the daily-maximum distribution histogram. Shipping 8 MB for one
chart is not worth it, so that chart's data is precomputed to JSON at build
time by the existing Python query. This breaks the shared-SQL rule
deliberately, and the exception is recorded here so it is not mistaken for an
oversight.

## Charts

**Visual parity is explicitly not a goal.** The two frontends share their data
and their colours, not their chart implementations. That was a constraint in an
earlier draft and it has been lifted, which frees the static app to use a
library suited to statistical display rather than one chosen to match Reflex.

**Observable Plot**, for three reasons:

- Grammar of graphics, so a chart is a handful of lines rather than a tree of
  configured components.
- **Native faceting.** The small-multiples grid of warming stripes, which the
  Reflex app assembles by hand from a grid of individual charts, becomes one
  mark with a `fx` channel.
- **It has a `cell` mark.** The month-by-year anomaly heatmap was cut from the
  Reflex app because Recharts has no heatmap mark at all, and it remains on the
  roadmap for that reason. `mart_climate_monthly` already holds the data and
  `climate_month_heatmap()` already computes it, unused. The static app can
  ship the view the Reflex app cannot draw.

DuckDB-WASM returns Arrow tables, which Plot consumes directly, so there is no
serialisation layer between query and chart.

The palette stays shared, because that is the cheap half of consistency: the
two sites should look like the same project even when the charts differ.

The static build gets its own Playwright assertions rather than a mirror of the
Reflex ones. The properties worth asserting are the same in spirit, axis
contrast in both colour modes and diverging colours resolving distinctly, but
they are checked against Plot's output, which has a different DOM.

## Deployment

`netlify.toml` at the repository root: build `web/`, publish `web/dist`, copy
the parquet into the published directory at build time.

The Render deployment is untouched. Both build from the same `main`.

## Testing

- The conformance suite, Python against TypeScript
- Palette generation, asserting the committed artifacts match `palette.py`
- Shared-SQL reference check, asserting no orphaned query files
- Browser tests against the static build, mirroring the Reflex ones
- Every existing test continues to pass unchanged

## Risks accepted

**First-load weight.** DuckDB-WASM is 3 to 5 MB before any data loads. On a
slow connection that is a real wait. It is the price of putting the query
engine in the browser, and it buys the absence of a backend.

**Two chart implementations, diverging by design.** The charts will look
different between the two sites, and that is now intended rather than tolerated.
The shared palette keeps them recognisably one project. Anyone comparing a
specific chart across the two should expect different marks, not a bug.

**Scope.** This is the largest piece of work in the project so far: 49 query
functions, 36 charts, a new build system and a new deployment target. Larger
than the temperature integration and the visualisation overhaul together.

## Decomposition

Three plans, each producing something that works on its own:

1. **Shared layer and conformance harness.** Extract the 15 static queries,
   generate the palette artifacts, build the conformance suite, and prove it by
   porting two or three query functions to TypeScript and watching the suite
   catch a deliberate divergence. No UI. This is the plan that de-risks
   everything after it.
2. **The static app.** Port the remaining dynamic query builders, build the
   React pages and charts, reach parity.
3. **Deployment.** `netlify.toml`, the data copy step, the browser suite against
   the static build, and documentation.

Each gets its own spec-to-plan-to-implementation cycle. Plan 1 is the one that
decides whether the approach holds, so it comes first and its conformance
harness must be proven to fail on a real divergence before plan 2 begins.

## Out of scope

Replacing the Reflex app. Both frontends are maintained; the Render deployment
remains canonical and is the one that gets new analytical features first.
